# Driftless

> **Docs that never drift. Driftless runs your docs to prove they work.**
>
> An always-on agent that keeps your documentation in sync with your code.

## Problem

Docs rot silently. Every merged PR can rename a flag, change a default, or remove an endpoint, and the README keeps describing the old behavior until a confused user files an issue. Reviewers rarely check docs, and nobody wants to audit every Markdown file after every merge.

## How it works

1. A PR is merged on a watched repo → GitHub webhook hits Driftless.
2. Driftless reads the diff and indexes `README.md` and `docs/**/*.md` into sections.
3. An LLM identifies sections the change made stale and rewrites only those.
4. A verifier checks each rewrite against the actual code.
5. Driftless starts the app and runs every request example in all the docs, fixing examples until they actually work.
6. Driftless opens a follow-up PR explaining every change, and remembers reviewer feedback for next time.

It also runs **before** the merge: on every push to an open PR it posts one comment with the stale sections, the proposed diff and the executed examples, sets a `Driftless / docs-in-sync` commit status, and commits the fixes to the PR's branch when someone replies `/driftless apply` (see [Pre-merge checks](#pre-merge-checks)).

Run it however suits you: as a CLI (`pip install`, see [Install](#install)), as a [GitHub Action](#use-as-a-github-action) with nothing to host, or as an always-on [webhook server](#running-as-a-github-webhook) with a [web app](#web-app).

## Install

Requires Python 3.11 or newer. Driftless is a normal Python package with a `driftless` command:

```bash
pip install git+https://github.com/debopamghosh12/driftless.git
# or, isolated from your other tools:
pipx install git+https://github.com/debopamghosh12/driftless.git
```

Then, in the folder you'll run it from:

```bash
driftless init                                  # asks for GITHUB_TOKEN and LLM_API_KEY, writes ./.env
driftless doctor --repo owner/name              # checks everything, prints ✅/❌ and how to fix each
driftless check --repo owner/name               # first run: audit every example in the repo's docs
```

- **Two secrets, nothing else.** `GITHUB_TOKEN` (a token with access to your repos) and `LLM_API_KEY`. The LLM endpoint defaults to Groq (`LLM_BASE_URL=https://api.groq.com/openai/v1`, `LLM_MODEL=openai/gpt-oss-120b`); point both at any OpenAI-compatible endpoint to change it. Settings come from environment variables or a `.env` in the current folder ([`.env.example`](.env.example) lists them all).
- **`driftless init`** asks for both secrets with hidden input and writes them to `./.env`. An existing `.env` is updated in place, other lines are kept, and pressing Enter keeps a value that's already there. It warns if `.env` isn't gitignored. Never commit it.
- **`driftless doctor [--repo owner/name]`** checks the Python version, that the secrets are set (never printing them), that the LLM endpoint answers and serves `LLM_MODEL`, and, with `--repo`, what the token may do there: read contents, and write contents, pull requests, issues and commit statuses (plus reading webhooks, optional). Write access is probed without changing anything: each probe POSTs an empty body, which GitHub rejects with 422 when the token is allowed and 403/404 when it isn't. Every ❌ says how to grant it for a fine-grained token, a classic token, and a workflow's `permissions:`. It exits 1 if a required check fails.

### Development

```bash
# create and activate the virtualenv (Git Bash on Windows)
py -3.11 -m venv .venv
source .venv/Scripts/activate

pip install -e ".[dev]"
```

## Usage

Sync the docs with a merged PR (no webhook needed):

```bash
driftless run --repo debopamghosh12/driftless-demo --pr 1            # opens/updates the docs PR
driftless run --repo debopamghosh12/driftless-demo --pr 1 --dry-run  # only print the proposed diff
```

This prints the PR's ChangeSet (changed symbols, env vars, routes, CLI flags), the doc sections most likely to be stale, the LLM's verified rewrites and new sections, and a diff. Without `--dry-run` it then pushes one commit to `driftless/pr-<n>` and opens (or updates) a PR titled `docs: sync docs with #<n> (...)`, printing its URL. If there is nothing to change, it comments on the source PR instead. `GITHUB_TOKEN` needs contents and pull-request write access.

## Executable docs

Driftless doesn't stop at reading the code: it **runs your docs**. Every request example in the docs is executed against the real app, started from the repo at the commit being documented, and an example only counts as correct if it actually works.

- **Examples** are `curl` commands in `bash`/`sh`/`shell`/`console` blocks, or raw requests in `http` blocks (`POST /notes` + headers + JSON body), aimed at `localhost`. Each is paired with its documented result: the first status with a reason phrase that follows it (`200 OK`, `HTTP/1.1 404 Not Found`) and the JSON block after that status. Examples that use shell variables (`$TOKEN`) or other hosts are skipped.
- **The app** is found with `ast` (a module-level `app = FastAPI(...)`, `src/` layouts included) and started with uvicorn on a free port. Its dependencies go into a venv cached under `.driftless_cache/venvs/`, keyed by a hash of `requirements.txt` and the Python version (built with `uv` when available, else `venv` + pip), so only the first run installs anything. **Code defaults are never overridden:** only env vars the code requires without a default (`os.environ["X"]`, pydantic-settings fields with no default) are set, to the value the docs document or else a typed placeholder. Every variable the code reads is removed from the inherited host environment. A doc that says `MAX_BODY_LENGTH` defaults to `1000` while the code says `10` therefore fails when run instead of being papered over.
- **Order matters, state doesn't leak.** Each doc file gets a fresh app, and its examples run in document order, so the `POST` that creates note 1 is what the later `GET /notes/1` reads.
- **Comparison.** The status must match. Documented JSON must match the actual JSON in structure: the same keys and the same value types. Ids and timestamps may differ freely. Other value differences (`"Pen"` vs `"Ink"`, 2 items vs 0) are warnings, not failures, since they usually reflect state rather than wrong docs.
- **Fixing, root causes first.** The LLM gets the *earliest* failing example: the example, its documented result, the actual request and response, and the route code. It fixes the request or the documented response, and the whole file is re-run on a fresh app (up to 2 fixes per example). The fix is then tidied deterministically: ids and timestamps from the live run are put back to the documented values, and unchanged JSON keeps its original formatting. When a fix changes a value in the request body (`"Milk"` → `"Tea"`), every documented response in the same file that echoes it is updated too: a field is changed only if it has the same key, the docs show the old value, and the live response with the fixed request returns the new one, and the file is run again to confirm. Later examples that pass after that re-run failed only because of the earlier one (a `POST /notes` rejected with 422 makes the `GET /notes/1` after it 404), so they are never "fixed" themselves. If the earliest failing example can't be fixed, the failures after it are left alone too, since they may be knock-ons. Each example ends up as **🧪 passed**, **🔁 fixed after running**, **⛓️ failed only because of an earlier example**, or **❌ still failing**. A failing example's doc change is kept, but flagged clearly in the PR.

In `driftless run` and in webhook syncs this happens after the static verifier, on **every** doc file (as the rewrites leave it), even when static analysis finds nothing stale. A PR that only changes runtime behavior, like a status code or a response field, breaks examples without touching any name the docs mention. Any example fixed after running goes into the docs PR, so such a PR still gets one. If examples fail and can't be fixed, and nothing else changed, the source PR gets a comment listing them instead of an "in sync" comment. The docs PR gets a "🧪 Executed examples: X/Y passing" section with a table (file, example, expected vs actual status, result) and lists every example fixed after running. Pass `--no-execute` (or set `EXECUTE_EXAMPLES=false`) to skip it.

### Docs health audit

`driftless check` runs every example in a repo's docs and needs no PR. You can point it at any repo with a FastAPI app:

```bash
driftless check --repo debopamghosh12/driftless-demo    # pass/fail report for main
driftless check --repo owner/name --ref v1.2.0           # any branch, tag or commit
driftless check --repo owner/name --fix                  # fix broken examples, open a PR
```

It exits with status 1 if any example is still failing, so it can gate CI. With `--fix`, the repaired files are committed to `driftless/fix-examples` and a PR is opened (or updated on reruns). As with docs PRs, a file that changed on the default branch since `--ref` is never overwritten.

> **Security note.** Executable docs **run the repository's code on your machine**: its `requirements.txt` is installed and its app is started. Only use it on repositories you trust. The app runs as a normal subprocess, not in a container. It is bound to `127.0.0.1` and gets a copy of your environment with credentials stripped (any variable whose name contains `TOKEN`, `SECRET`, `PASSWORD` or `API_KEY`). It is always killed afterwards, process tree included. Running it in a Docker sandbox with no network or host access is future work.

## Running as a GitHub webhook

Driftless can run always-on: every merged PR on a watched repo triggers the same sync as `driftless run` (analyze, rewrite, verify, open/update the docs PR). For local development, [smee.io](https://smee.io) forwards GitHub's webhook deliveries to your machine (Windows + Git Bash with Node installed).

1. **Set a webhook secret.** Put a random string in `.env` as `WEBHOOK_SECRET` (e.g. from `python -c "import secrets; print(secrets.token_hex(32))"`). `GITHUB_TOKEN` and `LLM_API_KEY` must be set too. Without a secret the server rejects every delivery.
2. **Start the server** (terminal 1):
   ```bash
   source .venv/Scripts/activate
   driftless serve            # http://127.0.0.1:8000
   ```
3. **Create a smee channel.** Open <https://smee.io> and click **Start a new channel**; copy its URL (`https://smee.io/<id>`).
4. **Forward the channel to the server** (terminal 2):
   ```bash
   npx smee-client --url https://smee.io/<id> --target http://localhost:8000/webhook
   ```
5. **Add the webhook on GitHub.** In the watched repo: **Settings → Webhooks → Add webhook**:
   - **Payload URL:** your smee URL (`https://smee.io/<id>`)
   - **Content type:** `application/json`
   - **Secret:** the same value as `WEBHOOK_SECRET`
   - **Which events?** *Let me select individual events* → tick **Pull requests** and **Issue comments** (untick *Pushes*)
   - **Active:** checked → **Add webhook**
6. **Check it.** GitHub sends a `ping` right away; the server log shows `POST /webhook 200`, and the webhook's *Recent Deliveries* tab shows a green tick. Merge a PR and watch the job:
   ```bash
   curl http://localhost:8000/runs     # last 20 jobs: status, timing, docs PR URL or error
   curl http://localhost:8000/health
   ```

How the server behaves:

- `POST /webhook` verifies `X-Hub-Signature-256` (HMAC-SHA256 of the raw body with `WEBHOOK_SECRET`) and returns **401** if it doesn't match.
- `ping` returns `ok`. `pull_request` with `action=closed` and `merged=true` queues a background **post-merge** sync and returns **202** immediately. `opened`, `synchronize`, `reopened` and `ready_for_review` queue a **pre-merge** check of the pushed head commit, an `issue_comment` whose first line is `/driftless apply` on an open PR queues an **apply** job (see [Pre-merge checks](#pre-merge-checks)), and `/driftless ignore|unignore|style|unstyle|memory ...` queues a **memory** job (see [Memory](#memory)). When one of Driftless's own docs PRs is closed, its changes are remembered as accepted (merged) or rejected (closed without merging). Other PRs closed without merging, drafts, other events on PRs from `driftless/` branches (Driftless's own, plus `docdrift/` branches from before the rename), other comments and other events are acknowledged with `ignored`.
- A PR is never synced twice at the same time: a redelivery while its job is queued or running returns `already running` with the existing job. A newer push, or the merge, **supersedes** a running pre-merge check instead (the response names the superseded job).
- Each job's start, finish, URL (docs PR, comment or commit) or error is logged; `GET /runs` returns the last 20 jobs from SQLite (they survive restarts), each with its `mode` (`pre-merge`, `post-merge`, `apply` or `memory`), the checked `head_sha`, the commit status it set (`check_state`) and, if it was replaced, `superseded_by`.

## Pre-merge checks

Driftless catches doc drift while the PR is still open, so the author fixes the docs before merging rather than in a follow-up PR.

- **What runs.** On `opened`, `synchronize`, `reopened` and `ready_for_review` (drafts are skipped until they're ready), Driftless runs the same analysis as after a merge, but at the PR's **head commit**: docs and code are read there, the verifier checks rewrites against that code, and the executed examples run against the app started from that commit. Doc edits the PR already makes count, so a PR that updates its own docs comes back green.
- **One comment, edited in place.** Driftless posts a single comment (found again by a hidden `<!-- driftless:pre-merge=N -->` marker) and edits it on every push. It says either **✅ Docs are in sync with this PR** (with what was checked: *N doc sections, M examples*) or what the PR breaks, e.g. **⚠️ This PR breaks 1 documented example (`POST /notes`) in 2 files** followed by *4 later examples failed as a result and pass once it's fixed.* Broken examples are counted by root cause; the knock-on failures are listed in a collapsed section. Then come a table of stale sections (file, section, why, the proposed fix and its verification), the proposed doc diff per file in collapsed blocks, the 🧪 executed-examples results, and *Reply `/driftless apply` to commit these doc fixes to this branch.* when there is something to apply.
- **Commit status.** The head SHA gets a status with context `Driftless / docs-in-sync`: `pending` while the check runs, `success` when the docs are in sync, and `failure` when there are stale sections or failing examples, with the counts in the description (e.g. `2 stale doc sections, 1 broken example (POST /notes)`). It links to the comment. If the check crashes, or an LLM review errors and nothing else was found, the status is `error` rather than a false green. Make it a required check in branch protection to block merging stale docs.
- **`/driftless apply`.** A comment that is exactly `/driftless apply` commits the verified fixes from the comment, as one commit on top of the PR's current head, directly to the PR's branch, and replies with the commit link. That push triggers `synchronize`, so the next check reports ✅ and turns the status green. Only users with **write** access (write, maintain or admin) can apply, and only to branches in the same repo: fork branches are refused with a reply saying why. If the branch moved since the comment, Driftless re-checks the new head before committing, and the push is a fast-forward, so a concurrent push is never overwritten.
- **Pre-existing drift isn't the PR's fault.** When the head has failing or fixed examples, Driftless also runs the docs at the PR's base commit (its merge base) against the app started from that commit. Examples that already failed there are *pre-existing drift*: they appear in a collapsed **Already stale on main, not caused by this PR** section, are marked *(pre-existing)* in the examples table, and don't count toward the failing status. Stale sections get the same treatment when it can be decided deterministically: the section is unchanged since the base, and every verifier problem in it that names something the PR touched was already a problem against the base code. Their fixes stay in the diff, so `/driftless apply` cleans them up too. Only drift the PR introduces turns the status red.
- **Newer pushes win.** A push while a check is still running supersedes it: the old job stops at its next checkpoint without commenting, and `/runs` shows it as `superseded`.
- **At merge time.** The post-merge sync still runs. If the docs were fixed before merging, it finds nothing stale and only comments that the docs are in sync (noting they were updated in the PR); no empty docs PR is opened.

The token needs **Commit statuses: write**, **Pull requests: write** and **Contents: write** (to push `/driftless apply` commits). Subscribe the webhook to **Pull requests** and **Issue comments**.

## Memory

Driftless learns per repo. (As a GitHub Action, the rules live in [`.driftless.yml`](#configuration-driftlessyml) instead.) Everything lives in one SQLite file (`DATABASE_URL`, default `sqlite:///driftless.db`) and is keyed by `owner/name`, so nothing leaks between repos.

**Commands.** Comment on any PR of the watched repo. Like `/driftless apply`, every command needs write access (checked with the collaborator-permission API) and gets a short reply:

| Comment | Effect |
|---------|--------|
| `/driftless ignore <file or heading>` | Adds an ignore rule. A file (`CHANGELOG.md`), folder (`docs/legacy/`) or glob (`docs/*.md`) matches by path; anything else matches a heading, case-insensitively, and covers its subsections (`Legacy API`). |
| `/driftless unignore <file or heading>` | Removes that rule. |
| `/driftless style <note>` | Stores a style preference, e.g. `use British spelling` or `keep examples minimal`. |
| `/driftless unstyle <n>` | Removes preference number `n`. |
| `/driftless memory` | Replies with the ignore rules, the numbered style preferences, and the docs-PR feedback. |

The command goes on the comment's first line. Quotes or backticks around the argument are dropped. Commands work on closed PRs too, since they change the repo's memory, not the PR.

**What the memory changes.**

- **Ignore rules** keep matching sections out of candidate selection, so they are never reviewed or rewritten. Files they match get no new sections, and their examples aren't run, in pre-merge and post-merge runs and at the base commit.
- **Style preferences** go into every review, retry and new-section prompt as *Maintainer style preferences for this repo*.
- **Feedback.** When Driftless opens or updates a docs PR, it saves the PR's changes (each rewritten or added section with a short diff and the model's reason, plus fixed examples). When that docs PR is **merged**, they are stored as accepted; when it's **closed without merging**, as rejected. The 3 most recent rejected changes go into the prompts under *Changes the maintainers rejected before*, telling the model not to propose the same kind of change again unless the code clearly requires it.
- **🧠 Remembered for this repo.** When an ignore rule kept something out of a run, or the model was given style preferences or rejected changes, the pre-merge comment, the docs PR body and the in-sync comment say so in one line, e.g. *🧠 Remembered for this repo: applied 1 ignore rule (`CHANGELOG.md`) · followed 2 style preferences.* An ignore rule only counts as applied if it removed a section that would otherwise have been reviewed, or a file with examples.
- **Job history.** Every webhook job is saved on each state change, so `GET /runs` survives restarts. Jobs a previous process left queued or running are marked `failed` with *interrupted: the server restarted before this job finished*.

## Use as a GitHub Action

Any repo can run Driftless in its own GitHub Actions, with nothing to host: no server, no webhook, no database.

1. **Copy the workflow.** Save [`examples/driftless-workflow.yml`](examples/driftless-workflow.yml) as `.github/workflows/driftless.yml` in your repo. It uses `debopamghosh12/driftless@v1`, triggers on pull requests, PR comments, a manual dispatch and a weekly schedule, and grants `contents`, `pull-requests`, `issues` and `statuses` write.
2. **Add the LLM key as a secret.** Get a Groq API key at <https://console.groq.com/keys>, then in your repo: **Settings → Secrets and variables → Actions → New repository secret**, name `GROQ_API_KEY`. The workflow's own `GITHUB_TOKEN` is used for GitHub, so no other secret is needed.
3. **Let it open PRs.** **Settings → Actions → General → Workflow permissions →** tick *Allow GitHub Actions to create and approve pull requests*, so the post-merge docs PR (and `fix` audits) can be opened.
4. **Optional: block merging stale docs.** Under branch protection, make `Driftless / docs-in-sync` (the commit status) or the workflow's job a required check.

What runs on each event (the same routing as the webhook server, in `driftless/events.py`):

| Event | What Driftless does |
|-------|---------------------|
| `pull_request` opened / synchronize / reopened / ready_for_review | [Pre-merge check](#pre-merge-checks): one PR comment, edited in place, and the `Driftless / docs-in-sync` status. With `fail-on-drift` (default) the job fails too when there is drift. Drafts and PRs from forks are skipped (fork PRs get no secrets and a read-only token). |
| `issue_comment` `/driftless apply` | Commits the fixes to the PR's branch. Pushes made with `GITHUB_TOKEN` start no new workflow runs, so the same job then re-checks the new head and updates the comment and status. |
| `issue_comment` `/driftless ignore`, `unignore`, `style`, `unstyle`, `memory` | Replies with the exact `.driftless.yml` change to make (see below), because a runner forgets everything when the job ends. |
| `pull_request` closed + merged | Post-merge sync: opens or updates the docs PR, or comments that the docs are in sync. |
| `workflow_dispatch` / `schedule` | [Docs health audit](#docs-health-audit) of the ref (`driftless check`). With the `fix` input, broken examples are fixed and a PR is opened. |

Inputs of the action:

| Input | Default | |
|-------|---------|---|
| `llm-api-key` | (required) | API key for the LLM endpoint, e.g. `${{ secrets.GROQ_API_KEY }}`. |
| `llm-base-url` | `https://api.groq.com/openai/v1` | Any OpenAI-compatible endpoint. |
| `llm-model` | `openai/gpt-oss-120b` | |
| `github-token` | `${{ github.token }}` | Needs the four write permissions above. |
| `fail-on-drift` | `true` | Exit 1 when a pre-merge check or audit finds drift, so the job can block merges. |
| `fix` | `false` | Audits: fix broken examples and open a PR. |
| `execute-examples` | `true` | Run the documented examples against the app. This runs the repo's code on the runner. |
| `python-version` | `3.11` | |

Outputs: `result` (what ran), `check-state` (`success`, `failure` or `error`) and `url` (the comment, PR or commit). Each run also writes a line to the job summary. `driftless action` is the command behind it: it reads `GITHUB_EVENT_NAME` and the payload at `GITHUB_EVENT_PATH`, so it can be tried locally with a saved payload.

## Configuration (.driftless.yml)

In Action mode, a repo's [memory](#memory) is a file instead of a database. Put `.driftless.yml` at the repo root:

```yaml
ignore:            # never review or rewrite these, and don't run their examples
  - CHANGELOG.md   # a file
  - docs/legacy/   # a folder
  - docs/*.md      # a glob
  - Legacy API     # a heading (case-insensitive), with its subsections
style:             # given to the model with every rewrite
  - Use British spelling.
  - Keep examples minimal.
```

Both keys are optional, and the rules mean the same as `/driftless ignore` and `/driftless style`. The file is read from the **default branch**, so a PR can't loosen the rules it's checked against. A malformed file fails the run with a message saying what's wrong. Commenting `/driftless ignore CHANGELOG.md` on a PR still works: Driftless replies with the whole file as it should read, the new line marked `# new`, ready to commit. Docs-PR feedback (accepted/rejected changes) isn't kept in Action mode, since nothing persists between runs. The webhook server (`driftless serve`) keeps using SQLite and the PR-comment commands.

## Web app

Everything above also works from the browser, with no CLI. `driftless serve` serves the web app from the same process as the webhook, at <http://127.0.0.1:8000/>.

![Driftless web app: repo dashboard with a docs health check](docs/web-app.png)
<!-- Screenshot placeholder: add docs/web-app.png -->

1. **Enable repos.** The web app acts with the server's `GITHUB_TOKEN`, so it only serves repos listed in `ALLOWED_REPOS` (comma-separated, `owner/name` or `owner/*`, e.g. `ALLOWED_REPOS=debopamghosh12/*`). Other repos get a "not enabled on this instance" page. If the list is empty, the web app serves no repo; the webhook is unaffected.
2. **Open a repo.** Type `owner/repo` on the home page. The dashboard shows the repo, its doc files (`README.md`, `docs/**/*.md`), its last runs, and five tabs:
   - **Docs health.** **Run check** is `driftless check` for any branch, tag or commit. It runs as a background job, and the page shows live stages (fetching repo, starting app, running examples, with the file being run) and then the results table (file, example, expected vs. actual status, 🧪/🔁/⛓️/❌). If examples fail, **Fix broken examples (open PR)** does what `check --fix` does and links the PR.
   - **Pull requests.** Recent open and merged PRs. **Analyze** is a dry run. On an open PR it is the pre-merge check at the head, base-commit classification included; on a merged PR it is the post-merge sync at the merge commit. It shows the stale-sections table with verification statuses, the colored doc diff and the executed examples, and posts nothing. The publish buttons queue the same jobs as the webhook. **Post pre-merge check** posts the one PR comment and sets the commit status. **Apply fixes to branch** is `/driftless apply`, run as the token's account (write access, same-repo branches only). **Open docs PR** runs on merged PRs. Each shows the resulting GitHub link. A publish within 30 minutes reuses the dry run instead of calling the LLM again, if the PR's head and the repo's memory haven't changed.
   - **Memory.** Ignore rules and style preferences with add/remove forms. They use the same storage and the same validation as the `/driftless` commands. The tab also shows the docs-PR feedback counts and the rejected changes shown to the model.
   - **Activity.** The repo's job history from SQLite (mode, PR or ref, status, duration, links, errors), refreshed every 3 seconds.
   - **Setup.** Whether `GITHUB_TOKEN`, `WEBHOOK_SECRET` and `LLM_API_KEY` are set (never their values), and whether a webhook delivers pull requests and issue comments as JSON. **Connect webhook** creates one for a public payload URL you enter (e.g. a smee channel), signed with `WEBHOOK_SECRET`. The token needs **Webhooks: read and write**. If GitHub refuses, the manual steps from [Running as a GitHub webhook](#running-as-a-github-webhook) are shown instead.

Long runs are always background jobs in the webhook's job store, so a request never waits on the LLM or the sandbox. A second **Run check** of the same ref while one is running shows that run instead of starting another. Pages never show secrets: payload URLs show only their host, and job errors are scrubbed of the token, webhook secret and LLM key. All repo content is HTML-escaped. Form posts from another origin are refused, so a page elsewhere can't start runs on your server. `EXECUTE_EXAMPLES=false` disables **Run check**, and the security note under [Docs health audit](#docs-health-audit) applies here too.

## Decision log

- **2026-10-26 — OpenAI-compatible LLM client (Groq, `openai/gpt-oss-120b`).** Using the `openai` SDK with a configurable base URL keeps us provider-agnostic; Groq gives fast inference. Because it's a reasoning model, all structured calls use `response_format={"type": "json_object"}` and are validated with pydantic.
- **2026-10-26 — SQLite via sqlmodel for memory.** Zero-ops persistence that's enough for decisions and reviewer feedback, with pydantic-style models shared with the rest of the code.
- **2026-10-26 — Config via pydantic-settings + `.env`.** One typed `Settings` object; secrets stay out of the repo (`.env` is gitignored, `.env.example` is committed).
- **2026-10-26 — Diff "before" = merge base, "after" = PR head.** GitHub's PR patches are three-dot diffs against the merge base, so comparing merge-base vs. head content matches the patches exactly; diffing against the merge commit would pull in unrelated commits from the base branch. Docs are read at the merge commit (what's live now).
- **2026-10-26 — Full-file AST first, patch reconstruction as fallback.** Python symbols come from `ast` on full before/after content (exact signatures, body-equality rename detection, pydantic `BaseSettings` fields as env vars). If content is unavailable or unparseable we rebuild partial text from the patch and use regexes (also the only path for JS/TS).
- **2026-10-26 — Heuristic candidate scoring before any LLM call.** Sections are scored by weighted mentions of changed terms (removed/renamed > signature change > modified > added; env vars/routes/flags boosted; code-span mentions boosted; plain lowercase words like `run` only count inside code). It's cheap, deterministic, explainable, and keeps the LLM prompt small.
- **2026-10-26 — Test files are excluded from the ChangeSet.** Test helpers and fixtures are never user-documented, and including them flooded the candidate list with noise.
- **2026-10-26 — Parallel doc blob fetches.** Fetching ~150 doc files serially took ~64s on `fastapi/typer`; an 8-thread pool cut a full run to ~21s without adding an async rewrite.
- **2026-10-26 — FastAPI routes come from the AST, linked to their handler.** Knowing the handler lets us report a changed decorator (`@app.put` → `@app.patch`) or a changed handler signature as one *modified* route, and report new handlers as their route rather than as an undocumented function. Express routes stay regex-based.
- **2026-10-26 — Route matching is method-aware.** `/notes/{note_id}` documented for GET/DELETE must not hide an undocumented `PATCH /notes/{note_id}`. Path-only mentions still count, at 0.3× weight.
- **2026-10-26 — Fuzzy rename = similar body (≥0.7) AND a shared name token.** `list_notes` → `fetch_notes` (0.83) is a rename; `farewell` vs `welcome` (0.89, no shared token) is not — tiny functions have near-identical ASTs, so similarity alone is unsafe.
- **2026-10-26 — Missing-docs suppression.** Skip route handlers (the route is reported), classes used in a changed handler's signature (request models are documented with the route), and renamed symbols whose old name is documented (that section gets rewritten). Items are deduped by name.
- **2026-10-26 — One LLM call per candidate section, JSON mode + pydantic, one corrective retry.** Every call uses `response_format={"type": "json_object"}`; the reply is validated (`stale`, `confidence`, `reason`, `updated_section`, plus "stale implies updated_section"). On failure we retry once, appending the model's bad reply and the validation error. Groq's 400 `json_validate_failed` is treated the same way.
- **2026-10-26 — Client-side TPM limiter + `reasoning_effort=low`.** Groq's free tier allows 8,000 tokens/min for gpt-oss-120b and each review costs ~2–3k tokens, so 4 parallel workers caused 429 storms that exhausted SDK retries. A sliding-window limiter (settled with real `usage`) paces calls instead; a full 13-call run takes ~4 min on the free tier with zero 429s. Both knobs are env-configurable (`LLM_TPM_LIMIT`, `LLM_REASONING_EFFORT`).
- **2026-10-26 — Missing docs are drafted after section rewrites, sequentially, interfaces first.** Items already mentioned by a rewrite (e.g. `NOTES_PAGE_SIZE` added to the Configuration table) are marked "covered" instead of getting a duplicate section. Routes/env vars go before functions so a function isn't documented as the endpoint wrapping it.
- **2026-10-26 — New-section placement is anchored on same-file siblings.** The example/neighbour section is chosen by mentions of other names from the item's own file (3× weight) plus diff identifiers, and the model only sees that file's hunks. Without this, the service function `update_note` was documented as the `PATCH` endpoint.
- **2026-10-26 — Edits are applied by line range, bottom-up, preserving section separators.** LLMs strip trailing blank lines, so a rewrite keeps the original section's trailing blank-line count; insertions go after the target heading's subsections.
- **2026-10-26 — Every LLM change is verified against the code at the merge commit before it's trusted.** A deterministic verifier (no LLM) checks: (1) signatures in headings/code spans/`def` blocks match the real definition's parameter names, order and defaults — FastAPI `Query(20)` unwraps to `20` and `int(os.getenv("X", "20"))` resolves to `20`, so `limit=NOTES_PAGE_SIZE` vs `20` is judged correctly; (2) new functions/classes/constants/env vars/CLI flags in code exist in the repo (imports and builtins count; names already in the original section are exempt); (3) documented `METHOD /path` and `curl -X` routes exist; (4) fenced Python parses; (5) lines that differ only in whitespace, table padding or typographic look-alikes (e.g. U+2011 non-breaking hyphens) are restored to the original, new table rows are re-padded, and rewrites touching a large share of unrelated lines are flagged. Failures go back to the model once, verbatim; a second failure drops the change. Each change is shown as ✅ verified, 🔁 fixed on retry, or ⚠️ dropped. Why: the previous run silently shipped a wrong default (`fetch_notes(limit=NOTES_PAGE_SIZE)` — that's the route's default, not the service's) and re-padded an unrelated table row; both are now caught deterministically.
- **2026-10-26 — Repo snapshot via one tarball request.** The verifier needs every source file at the merge commit, not just the changed ones. Downloading the tarball (read in memory, never extracted to disk) replaces ~150 per-file blob calls and supersedes the parallel blob fetching above.
- **2026-10-26 — One LLM call per doc file (batched sections), relevant hunks only.** Candidate sections from the same file share one prompt (up to 6 sections / 6k chars) with only the hunks matching their terms. On the demo PR this is 2 review calls instead of 9, and a full verified dry run takes ~2m15s on Groq's free tier instead of ~4m15s.
- **2026-10-26 — Missing items are documented in every file that covers their kind.** Routes/functions: any file mentioning ≥2 siblings (other routes; other names from the same source file). Env vars/flags: a single section must list ≥2 siblings, since they live in tables — otherwise `docs/api.md`'s passing mention of `APP_PORT` would get an env-var section. Siblings removed by the PR count, and if no file qualifies we prefer the file whose rewrite already mentions the item.
- **2026-10-26 — Docs PRs are one commit on the default branch, rebuilt on every run.** `pr_writer` creates the tree and commit with the Git Data API (one commit regardless of file count), then creates or force-moves `driftless/pr-<n>`. An open PR from that branch has its title and body edited, so reruns are idempotent and the PR always reflects the latest verified proposals. A file is only written if its content on the default branch still equals the merge-commit version Driftless edited. Otherwise it is skipped and listed, so someone else's later edit is never silently reverted. With nothing to commit, Driftless posts a comment on the source PR and edits that same comment on reruns (found by a hidden `<!-- driftless:source-pr=N -->` marker). PRs from `driftless/` branches are refused before any analysis, so Driftless never loops on its own PRs.
- **2026-10-26 — Section separators are structure, not content.** Trailing blank lines and `---` breaks are kept from the original section and stripped from the model's text. New sections go after the anchor's real content: before trailing "See ..." lines, blank lines and breaks. They copy the file's `---` style. Why: in a real run the model dropped one `---` and doubled another.
- **2026-10-26 — Invented example values are a verifier failure, not just a prompt rule.** The prompt forbids them, but the model still wrote `NOTES_PAGE_SIZE=30`. A new check fails any `NAME=value` for a repo setting whose value is neither the code's default (`os.getenv("X", "20")` defaults are indexed) nor a value already in the original section. The usual retry then fixes it: live, `NOTES_PAGE_SIZE=10` became `=20` on retry.
- **2026-10-26 — Webhook syncs run as in-process background jobs with an in-memory registry.** `POST /webhook` verifies the HMAC, then hands merged PRs to FastAPI `BackgroundTasks` and returns 202 at once, because a full sync takes minutes on Groq's free tier and GitHub times out deliveries after 10s. `jobs.JobStore` allows one queued/running job per repo+PR (a redelivery gets the existing job instead of a second LLM run), records status/timing/docs PR URL, and keeps the last 20 for `GET /runs`. No queue or worker process: one server and SQLite are enough for a hackathon demo, and syncs are idempotent, so a job lost on restart is fixed by redelivering the webhook. The server and CLI share the same steps (`sync.sync_pull_request` is the headless version); the app is built by a `create_app(settings, sync)` factory so tests inject a fake sync. A missing `WEBHOOK_SECRET` fails closed (every delivery is rejected).
- **2026-10-26 — Renamed DocDrift → Driftless ("Docs that never drift. Driftless runs your docs to prove they work.").** The new name says what the tool promises (docs that never drift), not the problem it fights, and the tagline leads with what sets it apart: every change is checked against the real code before it ships. The package, CLI command, logger names, default SQLite file (`driftless.db`), docs branch prefix (`driftless/pr-<n>`) and hidden comment marker (`<!-- driftless:source-pr=N -->`) all changed. Docs PR bodies now open with a "🤖 Generated by Driftless" banner, so reviewers see at once that a PR is automated. Two compatibility shims keep repos that already ran the tool safe: `docdrift/` branches are still treated as our own (never analyzed, so no loops on old docs PRs), and "in sync" comments with the old marker are edited on rerun instead of duplicated. The GitHub repo URL and the `docdrift-demo` repo keep their names.
- **2026-10-26 — Executable docs: run every example against the real app, fix it until it works.** Static checks prove that names and signatures exist. They can't prove that `curl -X POST ... → 201 Created` is what the API really does. So after the verifier, Driftless starts the app from the snapshot and runs each doc file's `curl`/`http` examples in order, on a fresh app per file. Statuses must match exactly and JSON must match in structure (keys and types), because those are what break a reader's code. Value differences are only warnings: the docs' `{"id": 7}` after a fresh start is state, not a bug. A failing example goes to the LLM with the actual request/response, gets fixed and re-run, up to 2 attempts. We chose a subprocess with uvicorn and a venv cached by requirements hash over Docker because it works on Windows + Git Bash with nothing else installed, and after the first install a check takes a few seconds per file. The trade-off is that it executes repo code locally, which is acceptable for trusted repos and is documented; container isolation is future work. Two things a live run showed: the model wrapped its fix in our `<example>` tags, and it pasted the run's own id and timestamp over the docs' example values. Both are now undone deterministically (`tidy_replacement`), in the same spirit as the verifier's minimal-diff restore. On Windows a venv's `python.exe` is a launcher with a child process, so the server is killed with `taskkill /T` (the whole tree); otherwise the real server would outlive the run.
- **2026-10-26 — Examples run in every doc file on every sync, not just the rewritten ones.** The point of executable docs is to catch drift that static analysis can't see. A PR that changes `POST /items` from 200 to 201 changes no symbol, route path or env var, so static analysis flags nothing and no file would have been "updated" to run. Now every doc file runs, with the rewrites applied, and an example fixed after running is enough to open a docs PR (`final_docs` merges example fixes in any file). The PR body then says static analysis found nothing and shows only the executed-examples section. Examples that still fail with nothing else to commit are listed in the source-PR comment, so Driftless never reports "in sync" while an example is broken. The cost is one app start per doc file with examples per sync, a few seconds once the venv is cached.
- **2026-10-26 — Pre-merge checks: same analysis at the PR head, one edited comment, a commit status, and `/driftless apply`.** Fixing docs after the merge means a second PR that someone still has to review; catching drift while the PR is open lets the author fix it in the same change. Pre-merge runs reuse the whole post-merge pipeline (`sync.analyze_and_propose`), only reading docs and code at the head SHA instead of the merge commit, so the verifier and executed examples judge exactly the code being proposed and doc edits already in the PR count. The PR gets one comment, found by a hidden `<!-- driftless:pre-merge=N -->` marker and edited on every push, so a busy PR never collects a comment per push. The status (`Driftless / docs-in-sync`) uses the plain statuses API, not the Checks API, because Checks requires a GitHub App and a personal token can already write statuses. LLM review errors give `error`, never a false `success`. Superseding is cooperative: a newer push (or the merge) flags the running job, which stops at the next stage boundary (after analysis, after the LLM, after examples) without commenting. The check also stops if the PR head is no longer the pushed SHA. We can't kill a thread mid-LLM-call, and a stale result posted after a newer one would be worse than a wasted call. `/driftless apply` commits the fixes cached from the last check at the same head, so it applies exactly the diff the comment showed without a second LLM run. If the head moved, it re-checks first. The commit goes on top of the head and the ref is only fast-forwarded, so a concurrent push fails instead of being overwritten. It requires write permission (checked with the collaborator-permission API, since `author_association` doesn't distinguish read from write collaborators) and refuses fork branches, where pushing would need the author's "allow edits" and a different remote. Apply jobs have their own lane in the job store, so applying never cancels a running check. The apply push fires `synchronize`, so the same pipeline confirms the fix and turns the status green; after the merge the post-merge sync finds nothing stale and only comments, since docs PRs are only opened when there is something to commit.
- **2026-10-26 — The app under test never gets the docs' defaults.** The live test on `driftless-demo` #5 changed `MAX_BODY_LENGTH`'s code default from 1000 to 10. The sandbox started the app with the docs' documented `1000`, so the old `POST` example passed and the drift was invisible: we were configuring the app to agree with the docs we were testing. Now only variables the code requires without a default are set (`os.environ["X"]` reads, pydantic-settings fields without a default). They get the documented value if there is one, else a placeholder typed from the cast or annotation (`int` → `1`, `bool` → `false`). Every variable the code reads is also stripped from the inherited host environment. The fixture's `GET /greeting` now runs with the code's `unset` instead of the docs' `hello`: a value warning, as it should be.
- **2026-10-26 — Pre-existing drift is classified against the PR's base commit, not blamed on the PR.** A required check that fails on every PR because `main` already has a broken example trains people to ignore it. When the head has failing or fixed examples, the base's docs run against the base's app (no fixer, so no LLM cost). An example counts as pre-existing when the same one already failed there, matched by file, label, n-th occurrence and documented status (so an example the PR edited is the PR's). We use the merge base, not the current tip of `main`, because that is what the PR's diff is against. For static sections the LLM can't tell us *when* something became wrong, so we decide it deterministically or not at all. A section is pre-existing only if it is unchanged since the base and every verifier problem naming one of the PR's matched terms was already a problem against the base code. LLM-only staleness, new problems, and unrelated standing problems (an unknown `HTTP_PROXY` mentioned next to the changed function) stay the PR's: under-claiming pre-existing drift costs a red check, over-claiming it hides real drift. Pre-existing items are listed in a collapsed section, excluded from the counts and the status, and mentioned in a green status's description; their fixes stay in the diff for `/driftless apply`.
- **2026-10-26 — PyGithub wrappers are tested against autospecs of the installed version.** `Repository.get_issue_comment` doesn't exist in PyGithub 2.10, and the free-form fakes happily accepted it, so the first comment edit crashed live. `edit_comment` now goes through `repo.get_issue(n).get_comment(id)`, which takes the PR number, so the protocol gained it. `tests/test_github_writer.py` drives every `GitHubWriter` method through `create_autospec` mocks of the real classes. Each method returns an autospec of the class its return annotation names, resolved lazily, so a missing method or wrong signature anywhere in a call chain fails the test.
- **2026-10-26 — Executed examples are reported by root cause.** On `driftless-demo` #6 the `POST /notes` example failed with 422, so the `GET /notes/1` and `DELETE /notes/1` after it 404'd, in both doc files, and the comment said "6 doc sections stale". Two things were wrong: the count (one broken example, not six) and the fixes (the fixer was asked to "fix" the 404s, which would have written the knock-on behavior into the docs). Now the fix loop works on the earliest failing example only, re-runs the whole file after each fix, and marks later examples that start passing as ⛓️ *failed only because of* that example. They're never sent to the fixer. If the earliest failure can't be fixed, later failures in the file are left alone with a note, because fixing them could encode a knock-on effect. This costs one app start per fix instead of one per round, a few seconds each, and usually saves LLM calls. Headlines and the commit status count distinct root-cause examples (`POST /notes` in two files is one), and the knock-ons go in a collapsed section. The "checked 0 related sections" wording, which counted only the sections the LLM reviewed, now says what was actually checked: every doc section, how many the model reviewed, and how many examples ran.
- **2026-10-26 — Memory: per-repo rules from PR comments, feedback from docs PR outcomes, jobs in SQLite.** Maintainers teach Driftless with PR comments (`/driftless ignore|unignore|style|unstyle|memory`) instead of a config file, because the moment someone wants Driftless to stop touching `CHANGELOG.md` is when they're looking at a Driftless comment. The commands go through the same write-access check as `/driftless apply`, since a style note ends up in every prompt. Each comment is its own job lane (keyed by comment id), so two commands never dedupe each other but a redelivered one does. Ignore rules are applied *before* candidate scoring, deterministically, not as a prompt instruction: an ignored section can't be rewritten even if the model disagrees. A rule is reported as applied only when it removed a section that top-k scoring would otherwise have kept, or a file with examples, so the 🧠 line isn't noise on every run. For feedback we save the proposed changes when the docs PR is opened or updated, keyed by its number, and resolve them on the `closed` event of our own branch, rather than re-fetching the PR's diff later: by then the branch may be gone, and we want our own per-section reasons and diffs, not a whole-file patch. Only the 3 most recent rejected changes go into the prompt. They cost tokens on Groq's 8k-TPM free tier, and recent rejections are the ones that reflect current taste. Accepted changes are counted but not prompted, since "do more of what you already do" adds no signal. Jobs are now saved to the same SQLite file on every state change (replacing the in-memory-only registry above). Jobs left queued or running by a dead process are marked failed on startup instead of showing as running forever. Tests use in-memory SQLite (`sqlite://` with a `StaticPool`, shared across the server's threads).
- **2026-10-26 — Happy paths stay happy: a fix may never turn a documented 2xx into an error.** On `driftless-demo` #7 (`MAX_BODY_LENGTH` default set to 2) `POST /notes` got a 422 and the fixer "fixed" it by documenting the 422. That example then passed, so the `GET`/`DELETE` 404s became the earliest failures and were "fixed" too: the docs PR turned three happy-path examples into error examples. Three deterministic rules now sit around the LLM, so they hold whatever the model replies. (1) A fix of an example that documents 2xx (or no status) must keep a 2xx. A downgrade is rejected before running, and the next attempt is told why, which steers it towards changing the request (a shorter body) instead. (2) A fix is kept only if the example passes when the file is re-run. A failing fix is thrown away, so the docs never get one that hasn't been seen to work. (3) A 404 on a resource whose create (`POST`/`PUT` on the same or a parent path) didn't return 2xx in this run is a certain knock-on. It is never sent to the fixer, and it's re-run only after the create is fixed. When no valid request succeeds, the example is ❌ *needs a human* with the model's reason, its docs are left unchanged, and the headline says so: "breaks 1 documented example (`POST /notes`): MAX_BODY_LENGTH=2 rejects the example body; needs a human. 2 later examples fail as a result." We enforce this in code rather than relying on the prompt alone (the prompt states the same rules) because the model has already ignored them once in a live run.
- **2026-10-26 — Web app: server-rendered pages on the webhook server, the same jobs, an allow list.** People who don't use the CLI should get every feature, but a second service or a JavaScript build would double what can break during a demo. So `driftless.web` is Jinja2 templates with htmx and Tailwind from CDNs, mounted in `create_app` next to `/webhook`. It reuses the job store, the SQLite memory and the syncer rather than re-implementing anything. `driftless check`'s body moved into `audit.run_audit`, which both the CLI and the web call. The web adds three job modes (`check`, `fix-examples`, `analyze`). Jobs report a stage (`fetch`/`review`/`start`/`run`/`baseline`/`publish`) through an optional progress callback threaded through `analyze_and_propose` and `run_audit`, and keep their full result in memory for rendering. Pages poll `GET /jobs/{id}`, since a run takes seconds to minutes and polling every 1.5s needs no websocket. "Analyze" is a dry run of exactly what the pre-merge check or post-merge sync would publish. The next publish of that PR reuses it once, within 30 minutes, at the same head and with the same memory, because on Groq's free tier a second LLM pass costs minutes. Otherwise publishing re-runs the full pipeline, exactly as a webhook would. Because every action uses the server's token, the web app serves only `ALLOWED_REPOS`, and an empty list means none (fail closed, like the webhook secret). `/driftless apply` from the web runs as the token's account, so the existing write-access check still applies. Pages show whether a secret is set but never its value. Job errors are scrubbed of secret values, webhook payload URLs show only their host, autoescaping is on, and cross-origin form posts are refused. That last one matters because a POST here can run repo code. Live testing caught one bug the fakes didn't: PyGithub's `PaginatedList[:n]` raises `IndexError` when the list is shorter than `n`, so the PR list uses `islice`.
- **2026-10-27 — Installable with `pip install git+https://...`: prompts and templates are package data.** The prompts lived in a top-level `prompts/` folder found via `Path(__file__).parent.parent`, which only exists in a source checkout, so an installed Driftless crashed on its first LLM call. They moved into the package (`driftless/prompts/*.txt`, beside the loader) and are read with `importlib.resources`; the web templates load through Jinja's `PackageLoader`. Both are declared as package data, and the install was verified in a fresh venv outside the repo (`--help`, `doctor`, `check` from another folder). The Groq endpoint and model were already the defaults, so a new user needs only `GITHUB_TOKEN` and `LLM_API_KEY`, which `driftless init` writes to `./.env` with hidden input.
- **2026-10-27 — `driftless doctor` probes write permissions with empty POSTs.** Classic tokens list their scopes in `X-OAuth-Scopes`, but fine-grained tokens and an Actions `GITHUB_TOKEN` expose nothing, and the repo's `permissions` field describes the user, not the token. GitHub checks access before it validates a body, so an empty POST to an endpoint that needs a permission answers 422 if the token has it and 403/404 if not, and nothing is ever created. One probe works for all three token kinds. Webhooks are only probed with a GET, because a webhook created by mistake would be a real side effect.
- **2026-10-27 — One event router for the webhook server and the GitHub Action.** `events.route_event` turns an event name and payload into a plan (pre-merge, post-merge, apply, memory, docs-PR feedback, audit, or ignored with a reason). The server queues jobs from it; `driftless action` runs the same plan inline in the workflow job. A PR comment or a draft means the same in both modes.
- **2026-10-27 — Action mode: memory in `.driftless.yml`, re-check after apply, skip fork PRs.** A runner's SQLite is gone when the job ends, so ignore rules and style notes come from a YAML file, loaded into an in-memory `Memory` so the pipeline code is unchanged. It's read from the default branch so a PR can't exempt itself. `/driftless ignore|style ...` comments reply with the exact file content to commit instead of pretending to remember. Commits pushed with the workflow's `GITHUB_TOKEN` don't trigger workflows (GitHub's guard against loops), so after `/driftless apply` the same job checks the new head itself, and the comment and status still turn green. Workflows on fork PRs get neither secrets nor write access, so pre-merge checks skip them with a reason instead of failing. `fail-on-drift` makes the job itself fail, for repos that gate on job results rather than commit statuses. Applies and memory replies never fail the job, since they're not checks. The example workflow cancels a superseded check through `concurrency`, which is what the server's job store does in-process.
- **2026-10-27 — `/driftless apply` commits the fixes the comment showed, from any process.** On the first real Actions run (driftless-demo #8) the comment proposed shortening the README's POST body to `"Mil"`, but apply ran on a fresh runner with no cached check, re-ran the LLM, and committed `"M"`: not what the reviewer saw. The server only avoided this because it kept the last check's fixes in memory, which a restart loses too. Now every check that has fixes also writes them as a commit on no branch, parented on the checked head (Git Data API, one call), and the comment carries a hidden `<!-- driftless:fixes {...} -->` pointer to it. Apply uses the in-memory fixes if it has them, else reads the files back from that commit when its head still matches, and only re-checks if neither is available (the branch moved, or the commit was garbage-collected). We chose a commit over embedding the fixes in the comment because comments are capped at 65,536 characters and doc files can be large. Since the fixer's first answer had also been a truncation, its prompt now asks for a short value that still means something ("Tea", not "Mil") when a value must shrink to fit a limit. `actions/setup-python` moved to v6, since v5 targets the deprecated Node 20.
- **2026-10-27 — A fixed request value is updated wherever later responses echo it.** On driftless-demo #8 the fix changed the README's POST body from `"Milk"` to `"Tea"`, but the `GET /notes/1` response further down still documented `"Milk"`: the docs contradicted themselves, and a value warning stayed behind. The fixer only ever sees one example, so this is done deterministically after a fix is accepted (`echo.py`), with no LLM call. Each scalar the fix changed in the request's JSON body becomes a (key, old, new) change. In the fixed example's own result and every later one in the file, a documented field is replaced only if it has that key, shows the old value, and the live response from the run with the fixed request has the new value at the same place. All of a response's `"key": old` fields must qualify, or none is touched. Request blocks are never edited, since a later request that sends the same value is its own example. The edit is textual, so formatting is kept, and it's kept only if a re-run of the file shows that no example that passed now fails. Requiring the live echo is what keeps it safe: a `"note": "Milk"` that the API doesn't echo, a list whose items don't line up with the response, or a second note created with `"Milk"` on purpose all stay as they are.
